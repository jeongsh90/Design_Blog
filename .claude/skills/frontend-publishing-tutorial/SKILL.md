# 프론트엔드·퍼블리싱 튜토리얼 작성

## 왜 실행 검증이 필수인가

코드 블로그 글은 독자가 그대로 복사해 자기 프로젝트에 붙여넣는다. 검증 없이 "이렇게 하면 될 것 같다"로 쓴 코드가 실제로는 안 되면, 독자는 시간을 낭비하고 이 블로그를 다시 찾지 않는다. 다른 축(디자인/AI)보다 코드 축은 특히 "실제로 되는지"가 콘텐츠 품질의 전부라고 봐도 된다.

## 코드 검증 절차

1. **최소 재현 파일을 scratchpad에 만든다.** 튜토리얼에 쓸 코드를 실제로 `.html`/`.css`/`.tsx` 등으로 작성해 Bash나 브라우저 도구로 실행/렌더링 결과를 확인한다.
2. **"동작 확인"과 "의도대로 보이는지 확인"은 다르다.** 에러 없이 실행됐다고 끝이 아니다 — 반응형 레이아웃이면 실제로 뷰포트를 바꿔보고, 애니메이션이면 실제로 재생되는지까지 본다.
3. **버전을 기록한다.** 사용한 브라우저, 프레임워크/라이브러리 버전(예: React 19, Tailwind CSS 4)을 draft에 명시한다. 프론트엔드는 버전 간 API 변화가 잦아 버전 없는 예제는 몇 달 안에 틀린 정보가 된다.
4. **검증하지 못한 예제는 절대 포함하지 않는다.** 시간이 부족하거나 실행 환경을 구성할 수 없으면, 그 예제는 draft에서 빼고 `<!-- 검증 실패: OOO, 제외됨 -->`으로 남긴다.

## 튜토리얼 구성 규칙

- **초기 상태 → 단계별 변경 → 최종 결과** 순서를 기본 골격으로 삼는다. 완성 코드만 던지면 독자가 "왜 이렇게 되는지"를 못 배운다.
- **코드블록에 언어 태그를 반드시 붙인다** (` ```css `, ` ```html `, ` ```tsx ` 등) — 티스토리 코드 하이라이팅이 언어 태그 기준으로 동작하므로, 태그가 없으면 편집 단계에서 색이 입혀지지 않는다.
- **"왜"를 설명한다.** 예: `display: grid`를 쓴 이유가 flexbox 대비 무엇이 나은지, `useEffect` 의존성 배열을 이렇게 둔 이유가 무엇인지. 코드만 나열하면 검색 결과 상위의 흔한 글과 차별화되지 않는다.
- **흔한 실수/함정을 한 군데에 모아 짚는다.** 실제로 헷갈리는 부분(예: CSS 우선순위, box-sizing 기본값)을 짚어주면 튜토리얼의 실용 가치가 올라간다.

## draft 말미 필수 섹션

```markdown
## 검증 기록
- 검증 환경: {브라우저/버전, 프레임워크/버전}
- 검증한 예제: {목록}
- 검증 못 한 예제: {목록 + 이유, 없으면 "없음"}
```

## 퍼블리싱(마크업/CSS) 글 특이사항

접근성(alt, 시맨틱 태그, 키보드 포커스)과 반응형 대응은 "선택 사항"이 아니라 퍼블리싱 튜토리얼의 기본 품질 기준으로 다룬다 — 이를 빠뜨린 예제 코드는 실무에서 그대로 쓰기 어렵다는 점을 명시한다.
