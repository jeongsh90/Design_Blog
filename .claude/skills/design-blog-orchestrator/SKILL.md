# 디자인 블로그 오케스트레이터

디자인/코드/AI 3개 축 콘텐츠를 **기획 → 작성 → 편집·포맷 → 발행 준비**까지 조율한다. 이 블로그는 자체 웹앱이 아니라 **티스토리**(외부 퍼블릭 블로그 플랫폼)에 올릴 콘텐츠를 만드는 것이 목적이다 — 최종 산출물은 "티스토리 에디터에 붙여넣으면 되는" 상태여야 하며, 실제 [발행] 버튼은 항상 사용자가 직접 누른다(계정 접근 권한이 없으므로 자동 게시를 시도하지 않는다).

**실행 모드: 서브 에이전트 (파이프라인 + 팬아웃 하이브리드)**
이 환경에는 TeamCreate/TaskCreate 팀 조율 도구가 없다. 대신 `Agent` 도구로 각 전문 에이전트를 순차/병렬 호출하고, `_workspace/`에 파일로 결과를 주고받는다. 콘텐츠 파이프라인은 실시간 상호 조율보다 "기획서 확정 → 그 기획서 기준으로 각자 독립 집필 → 한 명이 통합 편집"이 자연스러운 구조라 서브 에이전트 모드가 오히려 더 잘 맞는다.

## Phase 0: 컨텍스트 확인

작업 시작 전 `_workspace/`와 `posts/`를 확인해 실행 모드를 정한다.

1. `Design_Blog/_workspace/` 존재 여부와 최근 파일 확인
2. `Design_Blog/posts/` 하위에 이미 만들어진 포스트 폴더가 있는지 확인 (파일명 규칙: `posts/{YYYY-MM-DD}-{slug}/`)
3. 판별:
   - 사용자가 **특정 기존 글의 수정/보완**을 요청 → 해당 `posts/{slug}/` 폴더를 읽고 **부분 재실행**(관련 에이전트만 재호출, 나머지는 기존 파일 유지)
   - 사용자가 **새 글/새 주제**를 요청 → 새 슬러그로 새 `_workspace/` 세션 시작(기존 `_workspace/`가 있다면 `_workspace_prev_{날짜}/`로 백업 후 진행)
   - 사용자가 **블로그 전체 전략/카테고리 체계**를 요청 → strategist 단독 호출로 전략 문서(`_workspace/00_strategist_editorial-plan.md`)부터 작성

## Phase 1: 요청 분류

요청을 아래 4가지 중 하나로 분류하고 그에 맞는 Phase만 실행한다. 애매하면 AskUserQuestion으로 먼저 확인한다(특히 "블로그 전체 전략"과 "글 1편"은 작업 규모가 크게 달라 반드시 구분).

| 요청 유형 | 실행 Phase | 예시 |
|----------|-----------|------|
| 블로그 전체 전략/카테고리/에디토리얼 캘린더 | Phase 2만 | "블로그 카테고리 어떻게 잡을지 정해줘", "이번 달 뭐 쓸지 계획 세워줘" |
| 새 글 1편 작성 (주제 확정) | Phase 2(간이 브리프) → Phase 3 → Phase 4 → Phase 5 | "OOO 폰트 소개하는 글 써줘" |
| 기존 글 수정/보완 | 해당 축의 Phase 3 재호출 → Phase 4 | "저번 글에 예제 코드 하나 더 추가해줘" |
| 자료 아카이브 목록/정리만 | 해당 축의 writer만 단독 호출 (초안 없이 자료 목록/카탈로그 형태) | "쓸만한 무료 폰트 10개 정리해줘" (발행용 완성 글이 아니어도 됨) |

## Phase 2: 기획 (blog-strategist)

`Agent(subagent_type: "blog-strategist", model: "opus")`를 호출한다. 입력으로 사용자의 원 요청과 `_workspace/00_strategist_editorial-plan.md`(있으면)를 전달한다.

산출물: `_workspace/01_strategist_brief.md` — 다음을 포함해야 함:
- 이 글이 디자인/코드/AI 중 어느 축(또는 여러 축)에 속하는지
- 타깃 독자와 핵심 메시지 1줄
- 제목 후보 2~3개, SEO 키워드
- 어떤 writer 에이전트를 몇 개나 호출해야 하는지 (단일 축 글이면 writer 1명, 여러 축을 교차하는 글이면 여러 writer 병렬 후 통합)
- 카테고리/태그 제안

## Phase 3: 병렬 작성 (팬아웃)

브리프에서 지목된 writer(들)를 호출한다. **서로 독립적인 축이면 병렬로(각각 `run_in_background: true`) 동시에 호출한다** — 디자인 파트와 코드 파트를 같은 글에서 함께 다뤄야 하는 경우가 대표적이다.

- `design-content-writer` — 디자인 자료(로고/폰트/디자인 소스) 관련 파트
- `code-content-writer` — 프론트엔드/퍼블리싱 코드 관련 파트
- `ai-content-writer` — AI 프롬프트/스킬 자료 관련 파트

각 writer에게 `_workspace/01_strategist_brief.md` 경로를 전달하고, 결과를 `_workspace/02_{writer명}_draft.md`에 쓰도록 지시한다. 단일 축 글이면 해당 writer 1명만 호출한다.

## Phase 4: 편집·포맷 (tistory-editor)

모든 writer 초안이 완료되면 `tistory-editor`를 호출한다. 입력: brief + 모든 draft 파일 경로.

산출물 위치: `posts/{YYYY-MM-DD}-{slug}/`
- `final.html` — 티스토리 HTML 모드에 그대로 붙여넣을 최종 결과물
- `meta.md` — 제목/카테고리/태그/메타디스크립션/썸네일 지정/첨부파일 목록
- `attachments/` — 사용자가 원본 파일(폰트/이미지/프롬프트 텍스트 등)을 넣어야 할 자리 표시 폴더 + `README.md`로 어떤 파일을 넣어야 하는지 안내

tistory-editor는 SEO 체크리스트와 품질 검수(오탈자, 코드 실행 가능 여부, 저작권 표기)까지 수행한 뒤 통과 여부를 보고한다. 불통과 항목이 있으면 해당 writer에게 되돌려 1회 재작성을 요청한다(Phase 5-2 참고).

## Phase 5: 산출물 전달 + 피드백 루프

1. 완성된 `posts/{slug}/final.html`과 `meta.md`를 사용자에게 요약 보고 — 제목, 핵심 내용, 첨부해야 할 실제 파일 목록(사용자가 직접 준비해야 하는 것)
2. 발행은 사용자가 티스토리에서 직접 수행함을 명시 (계정 접근 불가 — Tistory Open API는 2022년경 신규 앱 등록이 막힌 이력이 있어 최신 상태를 가정하지 않는다. `tistory-publishing` 스킬 참고)
3. 실행 완료 후 피드백 요청: "톤이나 구성에서 바꾸고 싶은 부분이 있나요?"
4. 피드백은 Phase 7-2 표(하네스 스킬 본체 참고)에 따라 해당 에이전트/스킬에 반영하고 CLAUDE.md 변경 이력에 기록한다

## 에러 핸들링

- writer 중 하나가 실패(자료 부족, 근거 없는 주장 등)하면 1회 재시도 → 재실패 시 해당 파트를 빈 섹션으로 남기고 `final.html`에 `<!-- TODO: OOO 파트 보완 필요 -->` 주석과 함께 사용자에게 명시 보고. 다른 파트의 발행을 막지 않는다.
- tistory-editor가 저작권/라이선스 확인이 안 된 자료(예: 출처 불명 폰트)를 발견하면 **그 항목만 제외**하고 나머지는 진행, 어떤 자료가 왜 빠졌는지 `meta.md`에 명시한다. 임의로 라이선스를 추정해 넣지 않는다.
- 코드 예제가 실제로 동작하지 않으면(code-content-writer가 검증) 그 예제는 발행하지 않고 사용자에게 보고 — "동작하지 않는 코드"는 이 블로그의 신뢰도를 해치므로 절대 추측으로 채우지 않는다.

## 테스트 시나리오

**정상 흐름:** "무료 상업용 한글 폰트 5개 추천 글 써줘" → Phase 1(새 글, 디자인 축 단일) → Phase 2(strategist가 title/keyword/카테고리 확정) → Phase 3(design-content-writer 단독 호출) → Phase 4(tistory-editor가 라이선스 표기 검수 후 포맷) → Phase 5(`posts/2026-09-01-free-korean-fonts/` 산출물 보고)

**에러 흐름:** "Claude Code 훅 관련 프롬프트 모음 + 관련 프론트엔드 코드 예제 같이 넣어서 글 써줘" 중 code-content-writer가 제시한 예제 코드가 실행 실패 → tistory-editor가 검수 단계에서 발견 → 해당 섹션 제외하고 나머지(AI 파트)만 발행 가능 상태로 만든 뒤, 사용자에게 "코드 파트는 재검증 필요"로 명시 보고
